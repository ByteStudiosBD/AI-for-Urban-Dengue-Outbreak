## REAL DATA PROCESSING — STRICT DATA INTEGRITY
1. Inspect the supplied XLSX. It is expected to include `date`, `city`, `ward_id`, `population_density_sqkm`, `water_logging_risk_index`, `sanitation_score`, `avg_temp_c`, `max_temp_c`, `min_temp_c`, `rainfall_mm`, `relative_humidity_pct`, `dengue_cases`; verify exact casing/meaning and adapt if necessary. Parse Excel date serials correctly, normalize types, sort by `ward_id,date`, check missing and duplicates, and document data coverage.
2. Compute weekly rainfall lag columns (at least lag 1–4 weeks, and optionally rolling 2–4 week totals/means) via per-ward chronological grouping and `.shift()`/rolling windows, ensuring NO cross-ward contamination. Include temperature, humidity, relevant ward characteristics and calendar seasonality. Prevent data leakage from future weeks.
3. Define training examples for each forecast horizon `h in {2,3,4}` with target `dengue_cases` at `date + h weeks`, using only predictors available as of the selected reference date. Support explicit historical-as-of prediction and carefully label estimated future *cases* vs derived risk tiers. No same-week leakage and no use of future weather to predict historical targets.
4. Select a robust, reproducible baseline such as RandomForestRegressor or HistGradientBoostingRegressor; compare against a cheap seasonal/lag baseline if time. Serialize best validated horizon-specific models to `/models` using joblib and persist preprocessing/feature-order metadata. Predictions must be generated dynamically from real feature vectors. Never claim externally verified epidemiological precision.
5. Strict chronological train/validation/test split by date/target date (for example older years train, later year validation/calibration, newest year test if available); prevent horizon target leakage across split boundaries. Record the actual ranges. Calculate genuine held-out MAE and RMSE **for each horizon**, plus number of observations and optional error distribution. Never tune on test data. Support simple repeatable training command and model artifact loading for fast inference.
6. Derive `Low`, `Medium`, `High`, `Critical` from a clearly documented, defensible mapping of predicted weekly cases to ward risk using either pre-defined public-health rationale or thresholds based on the training distribution; make clear these are PROTOTYPE operational tiers, not official clinical advice. 8. Optimize: load model once, cache processed data and repeat requests with clear invalidation policy, avoid retraining on interactive requests, batch ward comparisons, document API-call minimization and LLM token cost as zero at inference if no LLM is used.
